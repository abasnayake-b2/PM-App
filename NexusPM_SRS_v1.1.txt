1. Introduction
1.1 Document Purpose
This Software Requirements Specification (SRS) defines the complete functional and non-functional requirements for DFN PM — a web-based project and resource management system. It serves as the contractual reference between stakeholders and the development team and provides the basis for system design, implementation, testing, and future enhancement.
1.2 Project Overview
Nexus PM is a modular, full-stack project management platform built to manage the complete software delivery lifecycle across multiple clients and projects. The system handles the hierarchy from geographic regions down to individual tasks, with resource allocation, issue tracking, SLA monitoring, time logging, and role-based access control for four distinct user roles.
System Identity
System Name:       DFN PM
System Type:       Web-based project & resource management platform
Architecture:      Modular monolith (Spring Boot) + React SPA
Database:          MySQL 8.0 with Liquibase migrations
Authentication:    JWT with role-based access control
Target Users:      Super Admin, Admin, Manager, Employee
1.3 Scope
Nexus PM covers the following functional domains:
Organisation management (Region → Country → Client → Project)
Release and sprint planning
Issue and task tracking with priority, SLA, and workflow management
Resource allocation with capacity planning and over-allocation detection
Time logging and utilisation reporting
Role-based access control with four hierarchical roles
Notifications, audit logging, and reporting dashboards

2.2 User Role Definitions
Super Admin
The Super Admin has unrestricted access to all system functions. This role manages the platform itself — system settings, all users across all departments, global audit logs, and role assignment. There must always be at least one Super Admin account. Super Admins can impersonate any user for support purposes.
Admin
Admins manage their organisation's configuration. They create and archive projects, manage clients, configure lookup tables (priorities, statuses, issue types, SLA thresholds), manage all users within their scope, and access all reports. Admins cannot change system-level settings.
Manager
Managers oversee their team's work. They create and edit issues, manage releases and sprints, set and view resource allocations for their team, and access team-level reports. Managers cannot create new users or modify organisation-level configuration.
Employee
Employees are the individual contributors. They view their own allocations and assigned issues, log time against tasks, update the status of their assigned items, and add comments. Employees have read-only access to other team members' data.
3. System Architecture
3.1 Architecture Overview
Nexus PM follows a modular monolith architecture. The backend is a single deployable Spring Boot JAR, internally structured as independent modules (packages) with well-defined boundaries. Each module owns its own controllers, services, repositories, DTOs, and entities. Modules communicate only through service interfaces — never directly through another module's repository. This design allows future extraction to microservices without rewriting business logic.
Architecture Decision: Modular Monolith vs Microservices
Decision:  Modular monolith chosen over microservices for this phase.
Rationale: Single deployment, single DB connection pool, simple transactions,
           no network overhead between modules, easier debugging and testing.
Future:    Module boundaries are designed so individual modules can be
           extracted to independent services when traffic or team size demands.

5. Authentication & Authorisation
5.1 Authentication Mechanism
Nexus PM uses stateless JWT-based authentication. No server-side session state is maintained. All authentication state lives in signed JWT tokens.

On logout, the refresh token is revoked in the database and the access token is blacklisted in Redis with a TTL matching the token's remaining validity. This prevents reuse of stolen tokens.

5.3 Security Filter Chain
Every inbound HTTP request passes through the following Spring Security filter chain:
CorsFilter — applies CORS policy (allowed origins from application.yml)
TenantResolutionFilter — resolves and sets tenant context (reserved for future SaaS)
JwtAuthenticationFilter — extracts JWT from Authorization header, validates signature and expiry, checks Redis blacklist, loads UserDetails, sets SecurityContextHolder
@PreAuthorize method-level guard — checks role claim against required roles
Controller executes business logic
GlobalExceptionHandler — maps exceptions to RFC 7807 problem+json responses

8. Use Cases
UC-01: Employee Login
Field
Detail
Use Case ID
UC-01
Name
Employee Login
Actor
Any user (unauthenticated)
Trigger
User navigates to /login and submits credentials
Preconditions
User account exists and is active. Account is not locked.
Main Flow
1. User enters email and password 2. System validates credentials against USER_AUTH table (bcrypt compare) 3. System checks account is not locked (failed_attempts < 5) 4. System generates access token (15 min, includes role, email, name, dept claims) 5. System generates refresh token (7 days), stores hash in DB 6. Access token returned in response body; refresh token set as HttpOnly cookie 7. Frontend stores access token in memory; redirects to Dashboard
Alternative Flow
A1 (Invalid credentials): Return 401. Increment failed_attempts. If failed_attempts = 5, lock account and send unlock email. A2 (Inactive account): Return 403 "Account inactive. Contact administrator." A3 (Account locked): Return 423 "Account locked. Check email for unlock link."
Postconditions
User is authenticated. SecurityContext holds user principal with role claims. Audit log entry created for login event.
Business Rules
Passwords stored as bcrypt hash (rounds=12). JWT signed with RS256 (asymmetric). Refresh token stored as SHA-256 hash only.

Use Case ID

UC-03: Issue SLA Breach Detection
Field
Detail
Use Case ID
UC-03
Name
SLA Breach Detection and Alert
Actor
System (scheduled job) + Manager
Trigger
Scheduled job runs every 15 minutes. Also triggered on issue status change.
Preconditions
Issue exists with a non-terminal status and a priority with SLA hours configured.
Main Flow
1. Scheduler queries all open issues where sla_due_at is approaching or passed 2. For each issue: compare NOW() against sla_due_at (adjusted for HOLIDAY_CALENDAR) 3. Compute status: Within SLA / At Risk (< 2 hours remaining) / Breached 4. If status changed since last check: update issue SLA status flag 5. If Breached: insert record into SLA_BREACH_LOG with breach_mins calculated 6. If Breached: send notification to assigned employee and their manager 7. Dashboard SLA widget updates on next poll
Alternative Flow
A1 (Issue resolved before breach): No breach log entry. SLA status marked as Resolved Within SLA. A2 (No assignee): Notification sent to project manager.
Postconditions
SLA_BREACH_LOG populated. Notifications sent. Dashboard reflects current SLA status.
Business Rules
SLA clock pauses when issue status = "Waiting for Client". Holiday calendar deducted from business hours. SLA breach is irreversible even if issue subsequently resolved.
UC-04: Project-Level Resource Utilisation Drill-Down
Field
Detail
Use Case ID
UC-04
Name
View Resource Utilisation for a Single Project
Actor

Trigger
User clicks a project row from the Dashboard, Projects list, or search results.
Preconditions

Main Flow
1. User clicks a project card or row 2. System navigates to the project detail view, defaulting to the Resource Utilisation tab 3. System computes: average allocation % across team (total capacity donut), billable vs internal split, hrs planned vs hrs logged this week per member 5. Business Rules
Utilisation % uses the same calculation as the global Resource Allocation dashboard (UC-02) but is filtered to project_id. Variance colour coding: green if actual is within 80-110% of planned, amber if 110-130%, red if actual is below 80% (under-delivery) or above 130% (significant overrun).
9. Sequence Flows
9.1 Authentication — Login & Token Refresh
The following describes the message sequence for user authentication:
Login Sequence
Browser          → POST /api/auth/login {email, password}
                 → AuthController.login()
                 → AuthService.authenticate()
                 → UserAuthRepository.findByEmail()
                 → PasswordEncoder.matches(raw, hash)
                 → JwtService.generateAccessToken(user, claims)
                 → JwtService.generateRefreshToken()
                 → RefreshTokenRepository.save(hash, userId, expiry)
                 → AuditLogService.logLogin(userId, ip)
Browser          ← 200 { accessToken } + Set-Cookie: refreshToken=...; HttpOnly
Token Refresh Sequence (silent, triggered by Axios 401 interceptor):
Browser          → POST /api/auth/refresh (cookie sent automatically)
                 → AuthService.refreshToken()
                 → RefreshTokenRepository.findByToken(hash)
                 → Validate: not revoked, not expired
                 → JwtService.generateAccessToken(user)
Browser          ← 200 { newAccessToken }
If refresh token is expired or revoked:
Browser          ← 401 → Frontend clears memory → Redirect to /login
9.2 Create Issue with SLA Computation
Create Issue Sequence
Frontend         → POST /api/issues {title, releaseId, priorityId, issueTypeId, assignedTo}
                 → JwtAuthFilter validates token, sets SecurityContext
                 → @PreAuthorize("hasAnyRole('MANAGER','ADMIN')")
                 → IssueController.createIssue(CreateIssueRequest)
                 → IssueMapper.toEntity(request)
                 → IssueService.create(issue)
                    → PriorityRepository.findById(priorityId)
                    → Compute sla_due_at = NOW() + priority.sla_resolve_hrs
                    →   Deduct HOLIDAY_CALENDAR non-working days
                    → RdIssueRepository.save(issue)
                    → NotificationService.notifyAssignee(issue)
                    → AuditLogService.log(CREATE, ISSUE, issueId)
                 → IssueMapper.toResponse(savedIssue)
Frontend         ← 201 { issue: { id, title, sla_due_at, status, ... } }
9.3 Resource Allocation with Over-allocation Check
Allocation Sequence
Frontend         → POST /api/allocations {employeeId, projectId, percentage, from, to}
                 → @PreAuthorize("hasAnyRole('MANAGER','ADMIN')")
                 → AllocationController.create(AllocationRequest)
                 → AllocationService.create(request)
                    → AllocationRepository.findOverlapping(employeeId, from, to)
                    → Calculate existingTotal = sum of overlapping percentages
                    → If existingTotal + newPct > 100:
                       throw OverAllocationException(existingTotal, breakdown)
                    → EmployeeLeaveRepository.findConflicts(employeeId, from, to)
                    → If leaveConflict: add warning to response (not block)
                    → AllocationRepository.save(allocation)
                    → NotificationService.notifyEmployee(allocation)
                    → AuditLogService.log(CREATE, ALLOCATION)
Frontend         ← 201 { allocation } OR
Frontend         ← 400 { error: "OVER_ALLOCATION", breakdown: [...], totalWouldBe: 110 }

11. UI/UX Design & Interactive Prototype
11.1 Design Approach
A fully interactive HTML/CSS/JS prototype was built ahead of backend implementation to validate navigation flows, information density, and the resource allocation experience with stakeholders. The prototype covers the complete primary user journey: login, dashboard, project drill-down, resource allocation (cards and timeline views), issue tracking, team management, sprints, time logging, reports, and notifications.
11.2 Theming — Dark & Light Mode
The interface supports both dark and light themes, switchable instantly from a toggle on the login screen and from the application sidebar. Theme state is implemented via a single data-theme attribute on the document root, with all colours defined as CSS custom properties that resolve differently per theme. This means no component markup changes between themes — only the underlying token values change.

11.3 Project Detail — Resource Utilisation View
Clicking any project (from the Dashboard, the Projects list, or search) opens a dedicated project detail page. This view directly supports the core resource-management requirement: knowing not just who is allocated company-wide, but specifically who is working on this project and how that compares to plan.
The view is organised into four tabs:
Resource Utilisation (default) — total capacity donut chart, billable/internal capacity breakdown, this-week-vs-plan variance per member, a card grid with one card per team member (allocation %, planned vs actual hours, open tasks, open issues), and a project-scoped 4-month allocation timeline.
Issues — the issue list filtered to this project only, reusing the same issue row component and detail panel as the global Issues page.
Releases — release cards showing Live / Active / Planned status with target dates and issue counts.
Timeline — a larger Gantt-style view of every team member's allocation across the project's active months.
Clicking any member card opens the same Person Detail slide-panel used elsewhere in the system, keeping the allocation editing experience consistent whether reached from the project view, the global Resources page, or the Team page.

15. Future SaaS Readiness
Although this delivery is a single-tenant system, the architecture has been designed to be SaaS-ready. The following decisions have been made now to minimise the cost of the SaaS migration when the time comes:
Decision Made Now
Future SaaS Benefit
UUID primary keys on all tables
No integer collision when merging tenant data
Shared module boundaries
Modules can be extracted to microservices per tenant load
Stateless JWT auth
Multiple API instances share no session state — horizontal scale is trivial
Redis for blacklisting
Shared Redis supports multi-instance deployment with no changes
Liquibase for migrations
Changelogs run per schema for schema-per-tenant SaaS model
Environment-based config
application-prod.yml injects secrets from environment — no code changes for SaaS deploy
Audit log on all mutations
Already compliant with SOC 2 audit trail requirements
Role system is table-driven
New TENANT_ADMIN role added to DB without code changes
Module-level service interfaces
Adding TenantContext threading to each service interface is a contained change
When SaaS migration is initiated, the primary code changes will be: (1) add tenant_id CHAR(36) to all 39 tables via Liquibase, (2) implement TenantContext + TenantResolutionFilter, (3) add Hibernate @FilterDef on all entities, (4) add TENANT table and provisioning service, (5) add Stripe billing module. All business logic remains unchanged.
